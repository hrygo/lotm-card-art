# 客户端多图高清加载与解码：最佳实践调研

研究日期：2026-09-15

研究范围：`apps/WorldOfMysteries` 在 macOS 26 上如何把「卡牌数量会增长到 220+、母版是 2K/4K PNG」这件事做得既清晰又不卡。研究对象是**客户端读取与解码**，不是出图工艺（出图工艺见 `2026-09-13-best-image-production-practice-research.md`）。

结论性质：本文是研究性建议，不是已批准的设计或实现方案。它不改变 `config/production-resolution-policy.json`（ADR-003）的交付规格，不构成任何视觉批准（D16），也不改变 `artifacts/**` 的不可覆盖 provenance 语义。凡涉及「App 内用什么样的衍生档」的落地，都需要单独决策记录。

## 结论先行

**「多图 + 高清 + 快」不能靠运行时把大图缩下来解决——必须靠「打包时就把每个显示尺寸做成一个物理上更小的文件」。** 本机实测：同一张 2048×3072 的卡，用 ImageIO 现缩到 800×1200 要 **65.8ms**，而直接读一个 800×1200 的成片只要 **2.7ms**；PNG 尤其极端，缩略图解码甚至比全尺寸还慢。

据此，四条主结论：

1. **档位按「显示像素」定，不按「交付像素」定。** 交付母版（2K PNG / 4K PNG）不进 App 包；App 里只放两个档：网格档（640×960）与详情档（800×1200）。
2. **格式分工：母版保持 PNG，App 内用 JPEG（速度）或 AVIF（体积）。** 实测解码速度 JPEG ≫ AVIF ≈ HEIC > PNG；文件体积 AVIF ≈ HEIC ≪ JPEG ≪ PNG。JPEG 是两者兼顾得最好的：比 PNG 小 5 倍、解码快 6 倍。
3. **4K 母版绝不能进 App 运行时。** 一张 4096×6144 解码后常驻 **100.7MB**、全解码 **205.7ms**；220 张在包内是 4.3GB。它只能是导出/印刷/分享的资产。
4. **解码永远离主线程，且每张每档只解一次**（已在 D22 落地）；缓存按**字节成本**限流，预取按可视窗口，离开可视区取消。

一句话：**运行时不做图像处理，只做「读已经合适的那一档」和「画」。**

## 1. 问题定义（本项目的具体数字）

| 事实 | 数值 | 来源 |
|---|---|---|
| 交付母版 | 标准 2048×3072、收藏 4096×6144，PNG/sRGB | `config/production-resolution-policy.json` |
| 仓库内真实母版 | 2048×3072 PNG 6.97MB ｜ 4096×6144 PNG 19.65MB | `artifacts/lotm.visionary.s07/render-v001/` |

| 网格瓦片实际显示 | 随窗口变宽：本机 1576pt 窗口下约 288pt → 2x 需要 577px 宽；窗口更宽则更大（列宽无上限） | `ArchiveRootView.AlbumHomeView` 的 `GridItem(.flexible(minimum: 165))` |

也就是说：**当前实现比「显示需要的像素」多解 1.25×（瓦片）到 1.6×（详情）线性尺寸**；而真正的风险在扩到 220 张、并且开始接触 2K/4K 母版之后。

## 2. 实测：格式与档位的真实成本

测量方法：本机 Apple silicon，`ImageIO`；每次测量新建 `CGImageSource`，三轮取最小值；解码一律带 `kCGImageSourceShouldCacheImmediately`（否则成本会被推迟到绘制，量到的是假数字）。素材为仓库内真实卡图。

**（a）解码成本发生在哪一步**（单张 1024×1536）

| 选项 | 创建 | 之后首次绘制 |
|---|---|---|
| 带 `kCGImageSourceShouldCacheImmediately` | **20.5ms**（解码在这里） | 1.9ms |
| 不带（默认） | 0.07ms | **21.3ms**（解码被推到绘制） |

Apple 文档对此有明文：该键默认 `false`，"causes decoding and caching to happen only when you render the image"。**这就是卡顿的根因形态**——不是「图太大」，而是「解码落到了帧提交路径上，而且每次重绘都重来」。

**（b）2048×3072 同图不同编码**

| 格式 | 文件 | 全分辨率解码 | 缩到 ≤1200 | 缩到 ≤512 |
|---|---|---|---|---|
| PNG | 6.97MB | 59.6ms | 65.8ms | 67.9ms |
| JPEG q85 | 1.39MB | **10.2ms** | 13.0ms | 10.3ms |
| AVIF q85 | 0.63MB | 36.2ms | 30.5ms | 48.0ms |
| HEIC q80 | 0.59MB | 44.6ms | 31.4ms | 48.4ms |

**这里有个反直觉但很关键的结果：PNG 的「缩略图解码」不省时间**（59.6 → 65.8/67.9ms，反而更贵，因为 ImageIO 必须全解再缩放）。**对 PNG 而言，唯一的降本手段是让文件本身更小。**

**（c）1024×1536 同图不同编码**

| 格式 | 文件 | 全分辨率解码 |
|---|---|---|
| PNG | 2.30MB | 17.1ms |
| JPEG q88 | 0.48MB | **2.9ms** |
| AVIF q85 | 0.24MB | 11.5ms |
| HEIC q85 | 0.22MB | 16.1ms |

**（d）按「显示尺寸」生成的衍生档**（从同一张 2K 母版生成）

| 档位 | 文件 | 大小 | 全解码 |
|---|---|---|---|
| 网格 560×840 JPEG q85 | 180KB | 1.4ms |
| 网格 560×840 AVIF q80 | 87KB | 7.9ms |
| 网格 640×960 JPEG q85 | 223KB | 1.8ms |
| 网格 640×960 AVIF q80 | 106KB | 7.9ms |
| 详情 800×1200 JPEG q90 | 344KB | 2.7ms |
| 详情 800×1200 AVIF q85 | 175KB | 17.8ms |

**（e）4096×6144 PNG（收藏母版）**

| 指标 | 数值 |
|---|---|
| 文件 | 19.65MB |
| 全分辨率解码 | 205.7ms |
| 缩到 ≤1200 / ≤512 | 253.9ms / 251.5ms |
| **解码后常驻内存** | **100.7MB**（4096×6144×4B） |

**（f）常驻字节（RGBA8，w×h×4）**

| 尺寸 | 常驻 |
|---|---|
| 4096×6144 | 100.7MB |
| 2048×3072 | 25.2MB |
| 1024×1536 | 6.3MB |
| 800×1200 | 3.8MB |
| 560×840 | 1.9MB |

**（g）包体推算（220 张）**

| 方案 | App 内体积 |
|---|---|
| 2K PNG 母版（现状规格直接进包） | ≈1.53GB ← 不可行 |
| 4K PNG 母版 | ≈4.3GB ← 不可行 |
| 2K JPEG q85 | ≈306MB |
| 2K AVIF q85 | ≈139MB |
| 1K PNG（当前档） | ≈506MB |
| 1K JPEG q88 | ≈106MB |
| **网格 640 JPEG + 详情 800 JPEG（建议）** | **≈125MB** |
| 网格 640 AVIF + 详情 800 AVIF | ≈62MB |

**（h）打包时生成衍生档的成本**：单张 2K → 800×1200，JPEG 约 0.09s、AVIF 约 0.17s。220 张 × 2 档 ≈ 40–75 秒，一次性，且发生在构建机上而不是用户机器上。

**（i）本机 ImageIO 可解格式**：`png, jpeg, heic, heif, avif, webp, tiff`。**不可解**：JPEG XL（`sips` 能列出但 ImageIO 不支持解码）。

## 3. 最佳实践清单

### 3.1 交付：衍生档在打包时生成，运行时不做图像处理

- 母版（`artifacts/**`）不动；App 内的每一档都是**打包时从母版生成**的派生物。落点就是现成的 `tools/production.py stage-app-resources`：它已经承担「按登记表把资源放进 `.app`」，把衍生生成挂在这一步，天然满足「`artifacts/**` 是唯一真源、不写回」。
- 好处：运行时零加工、可复现（同一母版 → 同一档）、可校验（每档文件名里带档位与编码参数，便于写门禁）。
- 反例（本项目已经踩过并已修）：在 `body` 里建 `NSImage`，把解码留给帧提交（D22）。

### 3.2 档位：按显示像素定档，并留一档余量

- 档位公式：`需要的像素 = 显示 pt × 屏幕 scale`。详情卡面固定 = 320×480pt → 2x = **640×960px**；网格瓦片的宽度则**随窗口变宽**（当前 4 列无最大宽度），本机 1576pt 窗口下约 288pt，宽屏上会明显更大。
- **先给瓦片设上限，再定档**：把网格列改成 `.adaptive(minimum: 165, maximum: 320)`（或等价的宽度上限），让瓦片永远不超过约 320pt → 2x 640px。没有上限的话，任何「够用」的网格档在超宽窗口上都会糊。
- 建议交付：**网格 640×960、详情 800×1200**（约 1.25× 余量），两档都能覆盖各自场景的上限。
- 只对「会大到明显不同的场景」再加第三档（例如未来的全屏查看/缩放）。**每多一档，就多一份包体与一份缓存**，不要预先铺开。

### 3.3 格式：母版 PNG，App 内 JPEG 或 AVIF

| 诉求 | 选择 | 依据 |
|---|---|---|
| 解码最快、生态最稳 | **JPEG q85–90** | 2K 全解码 10.2ms，比 PNG 快 6×；800×1200 只要 2.7ms |
| 包体最小 | **AVIF q80–85** / HEIC | 2K 0.63MB，比 JPEG 小 2.2×；代价是解码慢 3–6× |
| 交付母版 / 印刷 / 分享 | **PNG**（不变） | ADR-003 的交付规格 |

- **JPEG 与 AVIF 都是可见的有损**：这是**需要用户视觉确认**的改动（D16）。本机做过一次抽查——1024×1536 下 JPEG q88 相对 PNG 的平均逐像素差 2.88/255、p99 16、最大 42；暗带大面积渐变与左上角金饰两处 1:1 裁剪肉眼未看出差异（两张卡图本身带细颗粒，颗粒对压缩反而有利）。**这是抽样观察，不是视觉批准**；真实落地前应在最暗的渐变区与最细的金饰处做一次人工 A/B。
- 若坚持无损：只能靠「物理尺寸更小 + PNG」，此时包体与解码都明显吃亏（1K PNG 2.3MB / 17.1ms，对比 1K JPEG 0.48MB / 2.9ms）。

### 3.4 解码：离主线程 + 每张每档一次 + 显式立即解码

- `CGImageSourceCreateWithURL`（不缓存源）→ `CGImageSourceCreateThumbnailAtIndex`（网格档带 `kCGImageSourceThumbnailMaxPixelSize`）或 `CGImageSourceCreateImageAtIndex`（详情档）。
- **两个键都要显式给**：`kCGImageSourceShouldCacheImmediately: true`（把解码拉到创建这一步，也就是你想放后台的那一步）。
- 一律在后台线程；主线程只做缓存命中与绘制。
- 同一张同一档并发请求共用一次解码结果（已在 D22 落地）。

### 3.5 缓存与内存：按字节成本限流

- 用 `NSCache` + `totalCostLimit`，`cost = bytesPerRow × height`，而不是按张数限流——**同一张卡不同档差 10 倍**，按张数限流会失控。
- 分层预算示例（220 张规模）：网格档全驻留 220×1.9MB ≈ 418MB（太多，仍需限流）；实际只需驻留可视窗口 ± 预取，约 24 张 ≈ 46MB。详情档按张数上限（当前 24 张 ≈ 91MB，见 `ArtworkStore.heroPreloadLimit`）。
- 响应内存压力：监听 `DispatchSource.makeMemoryPressureSource`，收到 warning 就清缓存（比等系统杀进程体面）。

### 3.6 并发与优先级

- 解码是 CPU 密集的：并发上限 2–4 即可。实测单张成本（网格 1.4ms / 详情 2.7ms）意味着滚动一屏 12 张 ≈ 17ms CPU，两三个线程足够跟上。
- 优先级：可见区域 `userInitiated`、预取 `utility`；两者抢同一张时共用同一个 Task，不要各解一份。

### 3.7 网格：预取窗口 + 取消 + 占位

- 预取：可视区 ± 1 行；进入详情前预取相邻卡。
- 取消：离开可视区、切换区域、窗口关闭时取消未完成的解码。
- 占位：**低清占位必须是独立的小资产**（例如 32×48 内嵌在代码里），**不要**在运行时去缩大图——PNG 缩一次要 60ms+，占位反而变成卡顿源。

### 3.8 包体与资源布局（220+ 张时）

- 220 张 × 2 档 = 440 个文件：单文件小、目录大。分散文件对签名、备份、Spotlight 索引都有固定开销。**当文件数上千时**再考虑「单文件容器 + mmap 索引」（`CGImageSourceCreateWithDataProvider` 包一层自定义 `CGDataProvider` 指向 mmap 区域，零拷贝）。**这需要单独测量后再决定**，现在不是瓶颈。
- 不建议把卡图放进 asset catalog：编译进 `Assets.car` 后失去按档按需加载与按字节限流的自由度，而卡图恰恰是「档位 + 限流」收益最大的部分。

### 3.9 测量与门禁

- **静态/打包期**：每档文件字节数、档位尺寸是否符合公式（`宽 = 高 × 2/3`、长边等于档位值）、单文件与整批体积是否超预算；这些都能在 `stage-app-resources` 里断言。
- **运行期**：`os_signpost` 标注解码区间，用 Instruments 的 **Animation Hitches** 与 Time Profiler 看真实掉帧；`sample` 只能看趋势，**被遮挡的窗口会被系统跳过合成，数字只能当下限**（本会话已实测到这一点）。
- **回归**：把「详情档不得降采样」「不得在 body 解码」「每张每档只解一次」写成测试（已落 8 条，见 `ArtworkStoreTests`）。

## 4. 对本项目的具体建议（分阶段）

> **落地状态（2026-09-15 追加）**：下面的**第一步已实施**，决策见 `docs/DECISIONS.md` D23。实际参数与本稿建议有两处不同，原因如下——
>
> - **档位取 1200 / 1536，不是 640 / 800**：用户硬约束是「不降低打开单卡品质」，而改动前的实际解码尺寸是瓦片 683×1024、详情 1024×1536。取更低的档等于**同时降像素**，与约束冲突。改成「不低于改动前实际解码尺寸、只换编码不降像素」，速度收益全部来自 PNG → JPEG。
> - **列宽上限取 400pt，不是 320pt**：与 tile 档 800px ÷ 2 对齐。实测窗口 1576×971pt、四列时列宽约 293pt、卡面约 269pt，上限**当前不生效**；窗口宽超过约 1986pt（5K/6K 屏幕）才开始收敛列宽，届时瓦片仍不会被拉过 800px 成片。
>
> 实施后的实测数字：已安装 App 内 11 张 × 2 档共 22 次解码合计 **111ms**（首次冷启动 19.9ms，其余 3–7ms）；包内 `CardArt` 由约 33MB 降到 **15.22MB**；打包时生成 22 档耗时 **1.1s**。
>
> **仍未验证**：有损编码的视觉可接受性（须用户做 1:1 对比，D16）；端到端真机帧时间；220 张规模下的包体与内存（按单张实测外推）。

**第一步（现在就能做，收益立竿见影，不改变交付规格）**——以下为原始建议，保留为研究记录，实际取值以 D23 为准。

1. 在 `stage-app-resources` 里加一个「按档生成衍生档」的步骤：从 `artifacts/**` 的母版生成网格档（640×960）与详情档（800×1200），JPEG q85 / q90（可选同时出 AVIF 做对比）。
2. 网格列加宽度上限（`.adaptive(minimum: 165, maximum: 320)`），让瓦片不会随窗口无限变大。
3. `ArtworkVariant.tile` 上限改为 960、`hero` 保持「按源图分辨率解码」的口径不变——只是那时的源图本身就是 800×1200 的成片，于是「不降品质」与「快」同时成立。这是本方案最关键的一步：**把「不降采样」的含义从「运行时解大图」改成「交付尺寸就是显示需要的尺寸」**。
4. 包体预期：11 张 ≈ 6.2MB（现 33MB）；解码 1.8ms（网格）+ 2.7ms（详情），现为 19.2ms + 17.1ms。

**第二步（数量上来之后）**

4. 网格档改为按可视窗口限流 + 预取 ±1 行；详情档保留张数上限 + 内存压力响应。
5. 建立「档位—显示尺寸」的对照表并写进 UI 约定，避免以后有人随手把详情档改成 2048。

**第三步（只在真需要时）**

6. 需要放大/全屏查看时，再加一个「放大档」或在容器上做分块解码（`CATiledLayer` / mmap + ROI），而不是把 4K 母版塞进包。
7. 4K 母版只用于导出/分享/印刷；若将来做「导出到 4K」，导出路径直接读 `artifacts/**` 的母版，与 App 运行时完全隔离。

## 5. 风险与未验证

- **现状就有一个档位不足**（研究时的现状；已由 D23 解决）：网格档上限 1024px → 实际解出 683×1024，只有在瓦片宽度 ≤341pt 时才够用。本机当前窗口（瓦片约 288pt）没问题，但**在超宽窗口/大屏上把窗口拉满时，网格瓦片会被放大、变糊**。修法有二：给网格列加宽度上限（推荐，见 §3.2），或把网格档提到 960（2x 下覆盖到 320pt）。这条与本次性能改动无关，是档位公式本身的问题。**D23 两条都做了**：瓦片档提到 800×1200（覆盖 400pt），列宽上限也设为 400pt。
- **有损编码是可见变化**：JPEG/AVIF 的取舍必须由用户在最暗渐变、最细金饰、最亮高光三处 1:1 对比后确认（D16）。本文只做了抽样观察。
- **编码器未调优**：本文的 AVIF/HEIC/JPEG 都由 `sips` 默认参数产生，不代表最优编码（例如专门的 AVIF 编码器在相同画质下更小）。选型时应以「工具链能稳定复现」为准。
- **没有做端到端真机帧时间**：本轮只做了确定性的单张/整批微基准。真实掉帧要用 Instruments 的 Animation Hitches 跑一次滚动 + 打开详情的场景。
- **没有测「多档并发」互相抢 CPU 的情况**（例如快速滚动 + 同时打开详情）。
- **单文件容器方案完全未测**，只是列出备选。
- **AVIF/HEIC 的解码数字可能受软/硬解路径影响**：本机 HEIC/AVIF 的实测比 JPEG 慢 3–6 倍，与「硬件解码更快」的直觉相反，如实记录。
