# 诡秘之主原生卡牌画册 MVP 设计

用户已确认原设计方向；0.2.0 为 2026-09-13 方案审查后的契约澄清，
不将本轮细化冒充此前逐项批准。详见[审查记录](2026-09-13-lotm-card-studio-review.md)
及[实施计划](../plans/2026-09-13-lotm-card-studio-mvp.md)。

## 1. 设计结论

本项目新增一个独立的 macOS 原生客户端，暂名 `LotmCardStudio`。它首先是本地优先的卡牌画册、收藏册和语音阅读器，不是卡牌游戏，也不是 AI 自动发布器。

首期采用以下组合：

- 原生 macOS App 优先，未来再提供网页目录和分享能力；
- Git 仓库导入为 App 管理的内容库，不在 MVP 中直接编辑原始仓库；
- 新导入快照替换旧快照，按稳定 `card_id` 保留个人收藏与笔记；
- 内容数量为动态的 `0…N`，当前 220 个序列卡位只是脚手架容量，不是产品总数；
- 一卡一身份；一个序列可以有零张、一张或多张角色卡；
- 多张属于同一角色的卡通过 `character_id` 关联，但仍分别收藏、发声和展示；
- 默认静默，用户点击“唤醒”后卡牌才说话；
- 口头禅和唤醒语使用第一人称，故事采用第三人称档案叙述；
- MVP 只使用人工确认的台词与故事文本，由本机 SpeechRail 合成；
- 正式收藏、候选收藏和愿望清单分开；
- 画册首页采用“书架与画廊”，详情页采用“大卡面 + 右侧角色面板 + 故事抽屉”；
- 日常动效采用微光呼吸与灵性脉动，牌面显影只用于高序列或特殊事件。

现有仓库继续承担内容事实源、证据登记、视觉方案和结构检查职责。App 的个人数据、音频缓存和运行状态不回写公开内容源。

## 2. 当前基础与范围边界

当前仓库已经提供：

- `pathways/` 下的途径、序列和初始卡位；
- `card.json` 中的身份、扮演、能力、魔药、晋升和限制六维语义契约；
- `schemas/` 中的结构化数据契约；
- `sources/`、`references/` 和设计文档中的来源与素材边界；
- `production.stage` 的脚手架、研究、设计、出图、审核和批准流程；
- `tools/cardctl.py` 的检查、状态、任务编译和摘要能力。

当前仓库不是已完成的 220 张卡牌，也不是客户端数据库。很多卡牌仍处于 `scaffold`、未研究或未收录状态；App 必须把这些状态明确展示出来，而不能用空白内容伪装成完成。

### MVP 目标

用户可以：

1. 将本仓库导入为一个本地内容库；
2. 按途径、序列和角色浏览卡牌；
3. 查看正式卡牌、候选卡牌和待收录目标；
4. 收藏卡牌、加入候选收藏、加入愿望清单、添加标签和笔记；
5. 在用户主动点击后唤醒卡牌；
6. 听取人工确认的口头禅和故事；
7. 展开文字稿并查看内容状态；
8. 重新导入仓库新版本，同时保留未失效的个人记录。

### 明确不在 MVP

- AI 实时创作卡牌或故事；
- App 内修改原始 `card.json` 并直接提交 Git；
- 云端账号、多设备同步和多人协作；
- 网页客户端；
- 卡牌战斗、数值、牌组和联机规则；
- 自动连续播放全部卡牌；
- 将原著全文、第三方图片、模型、音频或凭据复制进公开仓库。

## 3. 产品信息架构

### 3.1 首页：书架与画廊

首页采用“书架与画廊”组合：

- 左侧是途径书架，列出当前内容库中的途径；
- 中央显示最近浏览、最近收藏和继续探索；
- 辅助区域显示已确认卡牌数、正式收藏数、候选收藏数和愿望清单数；
- “收藏画廊”提供网格、搜索、筛选和排序；
- 书脊墙是全途径浏览视图；
- 晋升星图作为后续探索视图，不作为 MVP 的唯一导航。

完成度分母必须根据当前内容库的已确认卡牌动态计算。`220` 只能作为脚手架容量或历史基线，不能作为永远固定的产品分母。

### 3.2 详情页：秘史书页

详情页采用三栏空间关系：

- 左侧：当前途径与序列导航；
- 中央：大比例卡牌正面，保持画册的视觉焦点；
- 右侧：身份、六维状态、收藏信息、音色信息和“唤醒 / 口头禅 / 故事”控制；
- 播放故事时，从底部展开故事抽屉，显示章节、文字稿、播放进度和来源状态。

声音控制以右侧角色面板为常驻入口，故事抽屉只在需要长文本或章节阅读时展开。卡底保留细小声波和播放状态作为视觉提示，不承担主要控制职责。

### 3.3 画册与工坊

产品保留两个工作区概念：

- `Album`：欣赏、收藏、唤醒和听故事；
- `Workshop`：证据、AI 提案、视觉生成、语音配方和审核。

默认在同一窗口中切换；用户可以把工坊另开为独立窗口。MVP 只交付 `Album`，工坊入口可以在后续阶段启用，不提前暴露未实现的编辑操作。

## 4. 卡牌身份与数量模型

### 4.1 序列不是卡牌

产品模型从固定的“一个序列一个卡位”升级为：

```text
Pathway
└── Sequence
    └── CardIdentity 0…N
```

`Sequence` 表示途径中的序列组织和晋升关系；`CardIdentity` 才是可展示、可收藏、可发声和未来可进入游戏的对象。

一个序列可以：

- 暂时没有实际卡牌；
- 有一张序列原型或角色卡；
- 有多位角色，各自形成独立卡牌；
- 在不同研究阶段从候选卡变为确认卡。

### 4.2 稳定标识

实现阶段必须区分以下标识：

- `slot_id`：旧脚手架中的序列级位置，例如当前的 `lotm.fool.s09`；
- `card_id`：实际卡牌的全局稳定标识，必须包含足够的途径、序列和身份区分信息；
- `character_id`：角色族标识，例如同一角色跨多个身份切片的聚合键；
- `identity_slice_id`：角色在某个序列、时期、身份或叙事状态下的具体切片；
- `variant_id`：同一身份卡的视觉、版式或收藏变体，不自动产生新的角色身份。

身份类型区分角色卡与序列原型；仅角色卡必须绑定 `character_id` 和
`identity_slice_id`。异画作为同一卡的变体集合，不复制顶层 `card_id`。

当前旧卡位不能静默当作已经确认的 `card_id`。导入器应保留旧 `slot_id`，将尚未完成身份确认的内容显示为序列级草稿或候选记录；身份迁移必须通过明确映射完成。

### 4.3 多个同名角色或同一角色多张卡

多个属于同一角色族的卡牌是合法的一等场景。它们：

- 共享 `character_id`；
- 各自拥有独立 `card_id`、序列、身份切片、卡面、故事和收藏记录；
- 在默认卡牌网格中分别出现；
- 在“角色族谱”视图中聚合显示时间线、序列关系和收藏进度。

同一身份的异画或收藏版本使用 `variant_id`；不同序列、时期、身份或叙事状态使用新的 `card_id`。具体原著归属必须以来源登记和事实核验结果为准，不能由角色名或模型推断自动建立。

## 5. 内容库导入与更新

### 5.1 导入流程

用户在 App 中选择仓库目录或可导入的内容包后，App 执行：

1. 检查内容包身份、路径和版本；
2. 校验 JSON 结构和当前支持的 Schema；
3. 检查途径、序列和实际卡牌数量；
4. 读取所有结构合法的记录，包括 `unfilled`、`proposed` 和未研究状态；
5. 排除 `.env`、模型、日志、原始音频、运行缓存和 `generated/` 运行产物；
6. 将内容和允许导入的图片资产复制到 App 管理的库目录；
7. 创建不可变的 `LibrarySnapshot` 清单；
8. 展示导入警告，让用户知道哪些内容只是草稿、候选或待收录。

导入失败时不得创建一个看似完整的半成品库。“部分导入”仅保留待修复候选和错误清单，
不得激活为活动库或静默丢弃卡牌、旧草稿及来源记录。可选图片缺失可以占位降级；
若批准依赖该图片，其正式资格也必须重新判定。

### 5.2 快照替换

新版本导入后替换当前活动快照。匹配规则如下：

- 相同 `card_id`：保留收藏、标签、笔记、播放历史和候选状态；
- 新增 `card_id`：进入未收藏状态；
- 内容哈希变化：标记“内容已更新”，使依赖旧文本或旧音色版本的音频缓存失效；
- 被移除的 `card_id`：保留个人记录，卡牌标记为“来源已移除”；
- `card_id` 改名或拆分：必须使用显式迁移映射，不能按名称相似度猜测；
- 空序列或新角色目标：允许用户手动加入愿望清单，不自动加入，也不计入正式收藏。

替换过程应具备事务性：新快照校验完成后再切换活动指针；失败时继续使用旧快照。

## 6. 收藏与状态

### 6.1 个人收藏

收藏数据使用本地优先数据库保存，且与内容快照分离。正式收藏、候选收藏和愿望清单是三个不同概念：

```text
正式收藏
└── confirmed 的实际卡牌

候选收藏
└── proposed / unresearched 的实际卡牌

愿望清单
└── 尚未形成实际卡牌的序列或角色目标
```

正式收藏进度只统计 `confirmed` 卡牌；候选收藏和愿望清单有各自的计数。`is_favorite` 独立于收藏类型，用户可以将候选卡标记为喜欢。

个人选择与当前内容资格分别保存：候选升级时提示可转正式，不自动代选；
正式卡批准失效时保留记录并标为待复核，暂不计入正式进度；来源移除不删除笔记与历史。
分子、分母都基于当前有效确认卡集合；分母为零时显示暂无已确认卡牌。

### 6.2 活动状态

以下是用户活动记录，不等同于制作状态或游戏解锁：

- `discovered`：用户打开过卡牌；
- `awakened`：用户完整播放过身份台词；
- `story_heard`：用户完整播放过至少一个故事章节；
- `last_opened_at`：最近打开时间；
- `heard_line_ids`、`heard_story_ids`：已听内容；
- `notes`、`tags`：个人内容。

未来游戏中的 `unlocked`、等级和战斗状态必须放在独立的游戏数据层。

## 7. 叙事与声音设计

### 7.1 叙事契约

每张卡牌是一位具有身份的叙事主体：

- `greeting`：第一人称身份唤醒语；
- `catchphrase`：第一人称口头禅；
- `story`：第三人称档案故事；
- 未来的 `reaction`：第一人称收藏或游戏反馈。

故事使用第三人称，是为了把角色沉浸感与事实叙述边界分开。故事仍由该卡牌绑定的声音讲述，不额外引入一个统一旁白，除非未来产品明确增加“档案馆旁白”模式。

### 7.2 内容来源分层

每段文本分别携带来源类别与编辑审核状态。来源类别为：

- `canon`：绑定已核验断言和来源；
- `interpretation`：基于事实的编辑性概括；
- `original`：原创演绎，必须明确标记。
编辑审核状态为 `draft`、`approved` 或 `rejected`，与来源类别独立。
只有真实人工批准记录存在，且被审核文本、人称、类型、引用与依赖摘要仍匹配时才可播放。
非 `draft` 标签或结构校验成功不能替代人工批准；原创文本也须批准。

MVP 只播放人工确认的文本。第二阶段才增加“事实骨架由人确认、AI 生成多个讲述版本”的能力；AI 变体需要记录事实快照、`claim_refs`、模型、提示词版本、生成时间和内容哈希，并经过人工批准。

### 7.3 音色绑定

声音采用三级绑定：

```text
CharacterFamily
└── base_voice_profile
    ├── IdentitySlice A：默认基础音色
    ├── IdentitySlice B：语气调整
    └── IdentitySlice C：明确 voice_override
```

同一角色默认保持声纹辨识度；身份切片可以调整语速、情绪、停顿和表达强度。特殊身份需要更换音色时，必须显式登记 `voice_override`，并单独经过可用性与连续性验收。

### 7.4 播放策略

- 默认不自动播放；
- 用户点击“唤醒”后才发起语音请求；
- 当前只允许一个卡牌占用播放焦点；
- 新的播放请求可以停止当前请求，但不能悄悄并行播放；
- 口头禅和故事在 App 管理的缓存目录中保存；
- 缓存键至少包含 `card_id`、内容 ID、文本哈希、音色版本、模型/profile 和输出格式；
- 文字稿始终可以展开，音频失败不应阻塞文字阅读；
- 内容或音色发生变化时，旧缓存必须被标记为过期。

### 7.5 SpeechRail 边界

卡牌 App 负责：

- 台词和故事文本；
- 播放队列、暂停、停止和重播；
- 本地音频缓存；
- 文字稿和播放记录；
- 用户可见的错误与重试。

SpeechRail 负责：

- 本机音色目录；
- 音色可用性；
- 文本到语音的生成；
- 音频流或音频文件输出。

App 使用独立的 `SpeechRailClient` 访问 loopback HTTP API，读取 `/health`、`/readyz` 和 `/v1/voices`，使用 `/v1/audio/speech` 合成已确认文本。它不复用 SpeechRail 当前 macOS 控制面 App 的 XPC 控制协议，不在卡牌 App 内启动、停止或下载 SpeechRail runtime。

SpeechRail 不可用时，画册、收藏和文字稿继续工作；只有播放能力进入不可用状态。典型错误需要映射为稳定的 App 状态：

- `speechrail_unready`；
- `voice_unavailable`；
- `tts_failed`；
- `audio_decode_failed`；
- `request_timeout`；
- `cache_corrupt`。

## 8. 原生客户端架构

### 8.1 模块边界

```text
LotmCardStudio
├── AlbumUI              画册、画廊、详情页、角色族谱
├── CollectionUI         正式收藏、候选收藏、愿望清单
├── CardDomain            Pathway、Sequence、CardIdentity、Narrative
├── LibraryImporter       导入、校验、快照替换和迁移
├── LocalStore            内容快照、个人数据、缓存索引
├── SpeechRailClient      loopback API 客户端
├── PlaybackCoordinator   原生播放、队列、打断和状态
└── FutureWorkshop        AI 提案、素材生成和审核，MVP 不启用
```

内容模型使用 `Codable` 和版本化 JSON 契约；个人收藏使用本地数据库，建议采用 SwiftData 或等价的本地持久化层。SwiftData 只能承载 App 运行时数据，不能取代 Git 仓库中的内容事实源。

界面使用 SwiftUI，涉及文件选择、窗口、菜单、拖拽和其他 macOS 特性时使用 AppKit 补充。初期构建目标为 Apple silicon `arm64`；未来需要支持 Intel Mac 时再发布经过实测的 universal binary。

### 8.2 内容与个人数据分离

App 管理库至少包含两类存储：

```text
ContentStore
├── LibrarySnapshot
├── Pathway / Sequence
├── CardIdentity
├── NarrativePack
└── imported asset metadata

UserStore
├── CollectionEntry
├── WishlistEntry
├── tags / notes
├── playback history
└── local preferences
```

用户删除或替换内容快照时，不应默认删除 `UserStore` 中的个人数据。正式删除个人数据应由用户在 App 中明确执行。

## 9. MVP 垂直切片

首个可运行样板不是 220 张卡牌，而是一个可完整验收的内容切片：

- 一条途径；
- 1–3 张经过实际研究或明确标记状态的卡牌；
- 如内容条件允许，至少两张共享同一 `character_id`，用于验证角色族谱和声音继承；
- 每张卡有一条人工确认唤醒语；
- 至少一张卡有一组口头禅和一个分章节故事；
- 至少一个空序列或待收录目标，用于验证愿望清单；
- 至少一个候选卡，用于验证候选收藏。

如果当前没有足够的已批准原著内容，演示数据必须明确标记为 `proposed` 或 `original`，只能验证界面和播放链路，不能被描述为正典完成卡牌。

### MVP 用户路径

```text
选择内容库
  → 导入并校验
  → 进入书架与画廊
  → 打开卡牌详情
  → 点击唤醒
  → 播放人工确认台词
  → 展开文字稿或故事抽屉
  → 收藏 / 候选收藏 / 加入愿望清单
  → 重新导入新快照并保留个人记录
```

## 10. 错误、隐私与权利

### 10.1 导入错误

导入错误必须包含稳定错误码、用户可读说明和受影响路径。校验失败不能覆盖当前活动库；用户可以查看错误清单后重新选择内容包。

### 10.2 语音错误

语音服务错误不能清空卡牌状态，也不能把“生成失败”写成“已播放”。当前卡牌保留文字稿、重试入口和服务状态提示。

### 10.3 隐私

- 收藏、笔记、播放历史和音频缓存默认只保存在本机；
- API key、模型路径、原始音频和完整运行日志不进入公开仓库；
- App 不因打开画册而自动上传内容或调用云端服务；
- 导入内容包时必须跳过敏感配置和运行产物。

### 10.4 权利边界

仓库现有 `NOTICE.md` 已明确主题内容不代表获得官方授权，代码许可证也不覆盖整个主题内容、第三方资产或模型输出。公开发行 App、音频或未来游戏前，必须单独核查适用的内容、字体、图片、声音和平台权利。App 的技术架构不能替代授权判断。

## 11. 验证与验收

### 导入与数据测试

- 动态卡牌数量不依赖 `220` 常量；
- 一个序列可以是零张、一张或多张卡；
- 同一 `character_id` 的多张卡可以聚合又可以独立收藏；
- `unfilled`、`proposed`、`unresearched`、`confirmed` 状态显示正确；
- 候选收藏和愿望清单不计入正式收藏；
- 新快照替换保留相同 `card_id` 的个人数据；
- 移除卡牌变为“来源已移除”，不静默删除历史；
- 内容哈希变化使对应音频缓存失效；
- 迁移映射缺失时阻止自动合并。

### 语音与交互测试

- 默认打开卡牌不发声；
- 点击唤醒后只播放当前卡牌；
- 播放中可以暂停、停止、重播和打断；
- SpeechRail 不可用时仍可浏览、收藏和阅读文字稿；
- `voice_override` 不可用时按明确规则回退或提示；
- 故事抽屉显示章节、文字稿、来源状态和播放状态；
- 正常内容、候选内容和原创内容不会混用标签。

### 测试隔离

- 单元测试使用 fake `SpeechRailClient` 和 fake audio provider；
- UI 测试不启动真实模型、不写用户真实库、不连接云端；
- 本地集成测试使用临时内容库、临时缓存和可控的 loopback fixture；
- 真实 SpeechRail 试听只作为本机验收，不作为 CI 必需条件。

MVP 的完成标准是：首个垂直切片可以在本机导入、浏览、收藏、唤醒、播放故事、展开文字稿，并在内容库替换后保持个人数据；不以“220 张已完成”作为验收条件。

## 12. 后续演进

### 阶段二：卡牌工坊

- 根据事实骨架生成 AI 叙事变体；
- 生成和审核 `narrative.json`；
- 设计音色预览与 `voice_override`；
- 生成视觉候选并绑定来源、哈希和审核记录；
- 导出内容包或 Git PR。

### 阶段三：游戏引擎

- 单独定义 `GameCard`、`RuleSet` 和游戏状态；
- 使用 `card_id` 关联画册卡牌，但不污染 `CardIdentity`；
- 先实现无界面的确定性规则模拟器，再实现战斗 UI；
- 游戏解锁和收藏关系只通过明确的应用层接口连接。

### 阶段四：网页与同步

- 先发布静态公共目录和分享页；
- 再评估账户、云端同步和协作编辑；
- 个人收藏与公开内容继续分离；
- 任何云端语音或 AI 后端都通过独立适配器接入，不改变本机 SpeechRail 契约。
